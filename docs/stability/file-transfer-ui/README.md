# File verification and keyboard action validation

The original native safety QR appears black. Both light/dark production dialog tests reproduce that zero-contrast image, and the original image-only file card produces no keyboard action. The repair uses an explicit white RGB image with black QR modules and adds a visible **Save or manage file** link to the existing file-card handler. Invalid/internal URLs never fall through to external URL launch; the existing transfer/state/generation checks still determine the action.

A second defect remains after the color fix: canonical safety data is binary CBOR, while the text QR encoder treats a zero byte as the end of input. An independent [ZXing decoder](https://github.com/zxing-cpp/zxing-cpp/tree/master/wrappers/python) reads only **22 of 172 bytes** from the intermediate production dialog bitmap. With binary encoding, it reads **all 172 identical bytes** from both light and dark bitmaps. The seven UI cases pass; [before](unit-before.txt), [after](unit-after.txt) and [manifest](validation.json) preserve the controls and scope.

Two disposable Mac clients restart, reuse their localhost certificate pins, unlock existing fixture identities and retain verified-peer labels. A generated 46-byte file reaches the recipient, whose log accepts Tab/Return on the new link and opens the native Save dialog. Saving into the explicitly selected private recipient directory produces byte-identical content, SHA-256 `445990b14ac558c0d929f89c2f8ec61a56051eb31f4a096672ee21909440c689`. This proves one developer-runtime native save after restart; it does not qualify large files, every platform pair or signing.
