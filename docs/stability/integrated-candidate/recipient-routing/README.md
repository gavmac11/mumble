# Nonrecipient relay negative

Three disposable clients joined the loopback-only private Mac server, verified its owned TLS certificate, and announced file-transfer capability. An opaque synthetic chunk declaring one recipient reached both the selected peer and a nonrecipient; the server correctly replaced the spoofed actor with the authenticated sender. The probe's first attempt had a 17-byte ID and was correctly rejected; the retained successful probe uses a valid 16-byte ID.

This verifies the operational channel-broadcast behavior and the need for recipient-only delivery. The proposed target field is unknown to the old protocol and is ignored. The running server's exact source head was not independently verified by this probe, and the payload is not a valid encrypted file/session. It does not qualify a new implementation, crypto completion, cross-transfer isolation, rates or backpressure. New clients must negotiate recipient-only capability and refuse unsafe old-server fallback; the updated relay must deduplicate/validate targeted peers and charge only actual recipients. Require real concurrent encrypted files with hashes and zero nonrecipient chunks on the exact final server source.
