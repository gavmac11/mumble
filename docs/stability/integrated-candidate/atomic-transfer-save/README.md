# Confirmed and failed transfer saves

The old failed-save fallback removed `target.part` even when that file already belonged to someone else. The unchanged production 17f0807e negative control reproduces that deletion. The replacement uses a private random stage owned by the save operation, and never touches a predictable `.part` path.

Manual existing-file replacement now requires an explicit plain-text Yes/No confirmation, defaulting to No, and rechecks the connection generation after the dialog. A confirmed worker request uses QSaveFile with direct-write fallback disabled, preserving the original if staging/commit fails. Unconfirmed creation copies in bounded blocks to an owned stage in the destination directory, then atomically publishes an exclusive hard link. Existing targets cannot be replaced; unsupported hard-link filesystems fail closed with the receive still Ready. The source is kept for retries and closed before receive cleanup. Automatic save-error events do not trigger an immediate retry loop.

Source 3119729df passes all three focused regressions (five Qt passes including initialization/cleanup): preserve existing target and unrelated `.part`, confirmed byte-exact replacement, and failed replacement preserving contents plus byte-exact retry. Full Mac Release client/server builds and all 41 enabled suites pass in 61.96 seconds (42 registered; OverlayTest disabled), including all 37 engine cases. Exact Opus 5.5 CLI review found a must-fix durability gap: explicit file/directory synchronization must precede success/receive cleanup. The review is retained and this revision is not promoted until that correction is qualified. Native Windows/Linux, installed confirmation UI, filesystem/disk-full/permission fault drills and shipping qualification remain pending. The test fixture's initial QTemporaryDir entryList compile error was corrected to use QDir; no production assertion was relaxed.

This does not fix unsafe automatic filenames, manual-save history changing the auto-save folder, trust identity freshness or server delivery/receipts. Non-hardlink target filesystems such as FAT/exFAT remain unsupported for create-only saves by this implementation; they are not silently overwritten.

## Checked synchronization correction

[Revision 09e9b92](revision-09e9b92/validation.json) checks file flush and fsync/_commit before both publication paths, checks Qt flush state and explicit stage removal, and then checks POSIX directory synchronization or a Windows published-file flush before Saved/receive cleanup. Windows directory-journal and physical power loss on any platform are not qualified. macOS fsync is checked; this implementation does not use F_FULLFSYNC. QSaveFile's native sync result is otherwise ignored by Qt, so this revision checks its stage explicitly before commit. Confirmed symlink destinations are refused to avoid following outside the requested directory.

All four injected sync-failure rows pass. Before publication, failures preserve the original or leave no new target/stage. After publication, the destination has already changed: the app reports that the file was written but synchronization/cleanup could not be confirmed, keeps Ready receive data, and never reports Saved. All four cases retry successfully with exact bytes. Nine focused passes and all 41 enabled Mac suites pass in 61.02 seconds, including 41 engine cases. Windows/Linux are running. The exact frozen Opus 5.5 follow-up found no new must-fix in the synchronization correction; its unverified Qt/Windows assumptions remain qualification limits. Earlier root records and the 48-case native Windows result qualify 311 source only, before the durability correction.

Named destination stages may remain after forced process termination; shared writable directory races, hardlink-incompatible filesystems, disk-full/power-loss and installed GUI qualification remain open. A cleanup error is reported rather than silently claiming Saved. No pattern-based deletion is added.

Qt QTemporaryFile.close does not close the OS handle, so its error state is not a proof of native-close error handling. Prepublication cleanup is observed in fault tests but its destructor return cannot be checked here. Postpublication stage removal is checked. Create-only POSIX saves are owner-only; confirmed replacements preserve target permissions.
